# Test Audit: Red Flags

Status: PRELIMINARY. Only RF-01 is verified in code at this stage (2026-10-30, branch `muse` at 7404ea8). Other areas are pending Research 01 and actual test runs. Do not treat this file as a final audit.

## RF-01: Reseller application is frontend-only and simulated, not a real request (CRITICAL, VERIFIED)

- File: `src/components/reseller/ResellerApplicationModal.tsx`, `handleSubmit`.
- Evidence: the handler contains the comment "Simulate real partner request dispatch", then `setTimeout(..., 800)` sets `isSubmitted` true. No API call is made in that handler.
- User-facing effect: after submit the modal shows "Application Received!", "Account Status: Under Review", and "Confirmation Sent To: <email>", even though no application record is created, no admin queue receives it, and no confirmation email is sent.
- Consequence: the reseller apply flow in the user brief cannot be tested end to end today, because there is no backend reseller-application endpoint, no application record, no admin queue, no approval action, and no notification to test. Research 02 widened the search and found only quota approve/deny/cancel, the modal itself, and `src/routes/reseller-info.tsx` importing it.
- Contrast: quota requests are real (Pending row in the reseller shard, admin approve in one transaction). Do not confuse the two flows.
- Required fix before this flow can pass: implement the recommended panel-plus-notification flow in `testing/plan/high-level-testing-plan.md` section 2, reusing the quota-request pattern, or explicitly decide the flow is out of scope and remove the misleading success/confirmation UI.
- Test cases that must pass after a fix: valid submit creates one Pending record and no account/quota/serial; duplicate email/company/prefix flagged; invalid input 400 with no record; same idempotency key creates one record; admin lists Pending sorted by SubmittedAt; non-admin 403; anti-self-approval; approve in one transaction with explicit quota only; double-approve does not double-grant; deny without a 10+ character reason rejected; denial reason retained; email link alone without an authenticated admin session changes nothing.

## RF-02: Quota approval writes one store, dashboard reads another (CODE FINDING, TEST PENDING)

- Approve writes shard `Quotas` + shard `LicenseLedger` in one transaction. Reseller dashboard gauge and shared quota endpoints read Root `ResellerQuotas` / `ResellerQuotaLedger`. No approve-path write to Root was found in code read. If the two stores disagree after an approve, dashboard numbers will be wrong even though the approve request succeeded. Test: approve, then read both stores immediately, then check the dashboard gauge.

## RF-03: Developer subscription limits not found in code, plan not even persisted (VERIFIED IN CODE)

- No subscription, plan, upgrade, or downgrade route or enforcement was found in developer controllers or `ProductService`. Product creation may not be gated by tier at all. Do not test "limit enforced" as if it exists; test creation beyond expected tier limits and record what actually happens.
- Follow-up search (GitMap, 2026-10-30): frontend `DeveloperRegisterForm` collects `SelectedPlan` and `DeveloperPlanPicker` offers it, backend `DeveloperRegisterRequest` validates it as `in:STARTER,ESSENTIAL,PRO,MAX`, and `DeveloperRegisterController` reads it into `$plan` and passes it to `buildSuccessResponse` only. `provisionDeveloperUser` sets Email, PasswordHash, TenantId null, IsActive, timestamps, and a role, with no plan field. User model has 0 `PricingPlan` hits, and `productLimit`/`product_limit`/`allowedProducts` have 0 hits across `backend/app`. So a developer's plan is collected at sign-up, echoed in the response, and not stored, not linked to a PricingPlan, and not enforced on product creation. Plan upgrade/change therefore has no persistence to test today, not just no limit check.

## RF-04: Gateway keys missing from Serials, and no key delivery email (CODE FINDING, TEST PENDING)

- webhookIssue writes `ProductLicenses` only, never `Serials`. PaymentWebhookService on a fresh shard skips its `Serials` write before creating the shard file. A gateway key can therefore verify via `ProductLicenses` but be missing where reseller serial lookup expects it. Also, no email delivery of the key was found in either gateway path; the key is returned in the webhook response only, so end-customer delivery depends on the developer's own gateway/software.

## RF-05: Two reseller tenant-binding paths can disagree (CODE FINDING, TEST PENDING)

- Strict path requires a tenant and fails 401/403/404. Loose preview path accepts header/query overrides and defaults to reseller id 1 / slug `alim`, swallowing bind errors. `MachineBindingController` also defaults `ResellerId` to 1 and falls back shard to root silently. This is a candidate cause for wrong-tenant or empty seat results surfacing as the generic server error, but the causal link is not proven in code alone and needs a reproduction case.

## RF-06: Dashboard counts come from different tables and shards (CODE FINDING, TEST PENDING)

- Developer activations from `HardwareBindings` vs reseller bindings from `MachineBindings`; developer overview from `database_path` only vs `repodb` mirror; trial counted by dealCode substring; admin totals hide unreachable shards behind `Warnings`. Cross-dashboard agreement cannot be assumed; it must be measured for one licence across all three dashboards.

## RF-07: Reseller Wholesale Studio shows hardcoded mock quotas, not live data (VERIFIED IN CODE)

- File: `src/components/reseller/ResellerWholesaleStudio.tsx`. No `useQuery`, fetch, or `lara-quota` call in the file. Quotas are `useState` initial values only: ESSENTIAL 500 allocated / 435 consumed, PRO_ANNUAL 200 / 65, plus two hardcoded custom offers. Any totals, gauges, or top-up UI in that studio do not reflect the reseller's real quota, and must not be used as a dashboard-sync test surface until it is wired to the live quota query.
- Related, also verified: frontend `/pricing` (`src/routes/pricing.tsx`) calls `getPricingTiers(isAnnual)` from `src/components/pricing/pricing-data.ts`, which returns static Starter $0, Pro $39 annual / $49 monthly, Enterprise $159 annual / $199 monthly. An admin price change in the database does not change that page today.
